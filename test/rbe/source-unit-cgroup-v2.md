# AMD64 cgroup-v2 unit presubmit

The Bazel 9 graph on upstream `f51a205a8` selects **all 360 runnable tests and 2,881 build-only targets** from the AMD64 cgroup-v2 unit row. The same submission also selects the native `uname` syscall test. Its Buildkite command is `bazel test --config=source-presubmit`. [Fork proposal](https://github.com/tamird/gvisor/commit/949d48715) · [Public Make target](https://github.com/google/gvisor/blob/f51a205a8/Makefile#L264-L269)

| What was verified | Result |
|---|---|

Each group maps one-to-one between the two revisions, including the original membership. [Complete analysis](https://github.com/tamird/gvisor/actions/runs/42240826638/artifacts/13517195079) |
| Action placement | Bazel assigned 366 test shard actions to OCI and five to Firecracker. The five are `cmd_test`, the runsc sandbox test, both sandboxexec binding tests and the native syscall. Ten Go compile actions and one C++ compile action sampled from the graph selected the ordinary OCI worker. [Action records](https://github.com/tamird/gvisor/actions/runs/42240826638/artifacts/13517195079) |
| Worker cgroup and cache | Both worker types returned cgroup2fs magic `0x63677270`, only hierarchy 0 and `IsOnlyV2() == true`. The OCI worker reported kernel `6.12.113+`; the VM reported `6.18.57`. Each test ran remotely with both values of `CGROUPV2`. Repeating `true` hit both remote cache entries. A v1 row still requires a real v1 fixture. ### Released LLVM compiler

The same Make recipe on the released LLVM integration selects 2,874 build-only targets and all 361 runnable tests including native `uname`. Compared with the original 3,242 roots, the compiler change adds five build targets and removes twelve, with no changes to the runnable set. The five additions are the systrap offset generator and its analyzer, the LLVM selection check, the vDSO linker script and the linked vDSO. [Compiler source](https://github.com/tamird/gvisor/commit/f6df263f8) · [Exact selection and label changes](https://github.com/tamird/gvisor/actions/runs/42263289691/artifacts/13526618022)

The original Bazel server exhausted its heap (exit 33). On the same source and worker configuration, sizing the server heap against available coordinator memory raised its observed maximum from 4.19 to 10.46 GB. The complete submission then recorded every one of the 3,235 roots. Of 2,874 build-only targets, 2,811 built, two explicitly failed and 61 ended with an unspecified abort. Of 361 runnable owners, 344 ran, two explicitly failed to build and 15 ended with an unspecified abort, including native `uname`. Of the original 297 blocked roots, 198 build-only targets built, 52 tests passed, the vDSO test ran and failed, and four build targets were removed. [Original memory failure](https://github.com/tamird/gvisor/actions/runs/42263289691/artifacts/13526618022) · [Full rerun and per-owner results](https://github.com/tamird/gvisor/actions/runs/42266767492/artifacts/13529188552)

Exactly 352 of 354 fresh remote shards passed. The sandbox suite repeated the default-route assertions covered by #15866. The vDSO checker reached `check_vdso.py:68` and could not start `readelf`. Three C++ compile actions failed while building the NVIDIA driver's Clang parser. The original diagnostics name the stateful `std::less<llvm::rdf::RegisterRef>` specialization in gVisor's pinned LLVM sources. LLVM later replaced that specialization. The separate configured shard-count query exited 1, so the total reported here counts only tests that actually ran. [Original five failure logs, projected to source locations](https://github.com/tamird/gvisor/actions/runs/42273255642/artifacts/13532960461) · [Upstream comparator fix](https://github.com/llvm/llvm-project/commit/a558d6560)

### Full remote run

One Bazel invocation reported a terminal build status for every target. Of 2,881 build-only targets, 2,650 built and 231 failed. Of 361 runnable owners, 295 built and produced a test result. The other 66 failed to build, including the native `uname` control. [All 3,242 target records](https://github.com/tamird/gvisor/actions/runs/42241955125/artifacts/13517404379)

| Test owners that ran | Fresh remote shards | Outcome |
|---:|---:|---|
| 293 | 303 | Passed |
| 1 | 1 | `//runsc/sandbox:sandbox_test` failed route assertions. |
| 1 | 1 | `//runsc/gofer/net:netgofer_test` timed out. |

The sandbox route assertions passed with the existing default-route change. The unchanged netgofer suite also passed once in that run. Repeating it on the original source hung on the seventh seccomp-child test. The child stack showed the netgofer waiting for its FD-based link while the receive worker continued processing batches after its peer closed. [Route change](https://github.com/google/gvisor/pull/15866) · [Separate target readbacks](https://github.com/tamird/gvisor/actions/runs/42247320345/artifacts/13518777315) · [Original repeat](https://github.com/tamird/gvisor/actions/runs/42248693170/artifacts/13519562956) · [Child stack](https://github.com/tamird/gvisor/actions/runs/42251755914/artifacts/13521745677)

On Linux, one batched receive after peer close filled all eight slots with zero-length records. The original packet receiver continued. Checking for a read hangup after an empty batch let all six existing netgofer cases pass in 25 repetitions and delivered the last frame in the focused package test. [Kernel result and matched tests](https://github.com/tamird/gvisor/actions/runs/42253668101/artifacts/13521985557)

The read-hangup change loses queued data in another case and is held. With eight empty records ahead of a 15-byte frame at shutdown, the original receiver continued. The candidate stopped even though the kernel still reported all 15 bytes queued. Manually running the next receive delivered the frame in all three trials per source. [Native queue measurements](https://github.com/tamird/gvisor/actions/runs/42255486185/artifacts/13522342638)

The first failed C compilation was `//tools/cstate_wake_probe:cstate_wake_probe`. Its wrapper invoked `x86_64-linux-gnu-gcc`, which the worker could not find. Registering the declared LLVM toolchain let the same worker compile and link the probe into a 16,752-byte AMD64 ELF. The FD parker’s genrule selected Clang too, then failed to include `asm/poll.h`. Applying the existing sidecar PR made the C compilation succeed. The link then failed on `-lpthread` and `-ldl`, before it produced an ELF or ran the FD parker tests. ### Comparison with the older integration

The original mixed smoke ran one logical test from the AMD64 unit row, atomicbitops. The broader unit profile on that older source selects 319 of the 360 by their upstream labels. [Original six remote results](https://github.com/tamird/gvisor/actions/runs/42232937931/artifacts/13510273674)

| Selection on Linux AMD64 | Runnable tests | Same runnable label upstream | Build-only targets |
|---|---:|---:|---:|
| Upstream Make, f51a205a8 | 360 | 360 | 2,881 |
| Fork mixed smoke, 9fd10bc0c | 6 | 0 exact, 1 architecture wrapper | 0 |
| Fork unit profile, 9fd10bc0c | 340 | 319 | Analysis failed on visibility |
| Public Make roots and flags on the same fork | 336 | 323 | 2,812, including 2,667 with the same upstream label |

**Fix the selector and refresh the source separately.** On the same fork checkout the public roots and filters restore four runnable tests and remove eight. The restored owners are coretag, metric, trace and tracereplay. Upstream deliberately returned each to unit CI. The eight additional fork owners are two runner tests and six test utility tests. The fork can retain them as additional checks. They do not replace an upstream owner. [Fork patterns](https://github.com/tamird/gvisor/blob/9fd10bc0c/test/unit.targets) · [Coretag](https://github.com/google/gvisor/commit/9da6f49c8) · [Metric](https://github.com/google/gvisor/commit/a52b53673) · [Trace](https://github.com/google/gvisor/commit/418508a78) · [Tracereplay](https://github.com/google/gvisor/commit/0068142bd)

With the correct selection on the old source, 37 upstream runnable labels remain absent and 13 fork labels are extra. Some are genuine new workloads. The fork lacks the Go example package that supplies `//examples/sandboxexec/go/docprocessor:docprocessor_test`. Others reflect package moves. For instance, the extension test source moved byte-for-byte from `runsc/fsgofer/extension` to `runsc/gofer/fs/extension`. A rename establishes source lineage. It does not establish that a historical test ran against current code. [Example package](https://github.com/google/gvisor/blob/f51a205a8/examples/sandboxexec/go/docprocessor/BUILD) · [Full label comparison](unit-cgroup-v2-owners.tsv)

The broader fork profile has one additional build-only failure. Selecting `test/runner/...` reaches `//test/runner:defs_bzl`, which depends on `//test/rbe/tcg:defs_bzl`. The latter declares a dependency on the private `//tools/bazeldefs:defs_bzl`. Bazel reported the visibility error before execution. The upstream row excludes this fork-only runner root. If the fork retains that full additional build, its metadata needs package-scoped visibility for the actual caller. [Runner dependency](https://github.com/tamird/gvisor/blob/9fd10bc0c/test/runner/BUILD#L49-L57) · [TCG dependency](https://github.com/tamird/gvisor/blob/9fd10bc0c/test/rbe/tcg/BUILD#L126-L133) · [Private definition](https://github.com/tamird/gvisor/blob/9fd10bc0c/tools/bazeldefs/BUILD#L114-L122)

**Keep the cgroup cache key and qualify placement.** Public Make observes the host cgroup filesystem and passes `--test_env=CGROUPV2=true` on this row. The fork's broad unit profile omits the setting. The runtime detects the real filesystem with `statfs`. A configuration carrying `CGROUPV2=true` still needs a test worker with an actual cgroup-v2 mount. The fork's v1 transition already replaces that environment entry with `false` for its own tests. The earlier native cgroup-v2 run on a GitHub runner executed 471 named cases in two packages. The six-target RBE receipt does not record the remote workers' cgroup filesystems. [Host detection](https://github.com/google/gvisor/blob/f51a205a8/runsc/cgroup/cgroup.go#L127-L135) · [V1 transition](https://github.com/tamird/gvisor/blob/9fd10bc0c/tools/bazeldefs/cgroup_test.bzl#L14-L23) · [Earlier native cases](https://github.com/tamird/gvisor/actions/runs/41495497730/artifacts/13166333421)


## Reading the comparison

The [owner matrix](unit-cgroup-v2-owners.tsv) lists the exact Bazel labels and their [configuration checksums](unit-cgroup-v2-configs.tsv). `run` means Bazel selected a runnable test. `build` means the full row selected a target only for building. A dash means absent. A question mark in the fork-unit column means the label was outside the runnable set and its build-only status is unknown. A slash distinguishes the original full-row configuration from the test-only analysis configuration if they differ. Configuration checksums describe the recorded source, Bazel version and flags. Equal label spellings across sources establish a selection match, not a new execution result.

The one-job comparison analyzed each command twice, first with its ordinary selection and then with `--build_tests_only`. In the ordinary upstream selection, 721 Nogo rules and three KVM-requiring rules have a Bazel test size but are excluded from the runnable set. The Linux coordinator reported `cgroup2fs`. It used Bazel 9.3.1 upstream and 8.8.1 on the older fork. The analysis retained the fork's RBE platform declarations, disabled action execution with `--nobuild`, and used local strategies for this credential-free inspection. [Qualification source](https://github.com/tamird/gvisor/blob/05d4b5e3d/.github/qualification/source_unit_selection.py) · [Original configurations and events](https://github.com/tamird/gvisor/actions/runs/42237226044/artifacts/13514900263)

The workflow ended red. Its historical reader rejects full-root no-build results, and the broader fork profile genuinely failed on the visibility edge above. For every reported complete profile, the original events pair every configured label and configuration with its `NO_BUILD` or `SKIPPED` result, with zero test execution events. The measured counts use those original records. The broad fork profile's failed full-root selection contributes no build-only count.
